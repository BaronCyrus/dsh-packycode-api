# Changelog

## 1.3.8

- **DSH's official 自动审查 can review with jev-latest or DeepSeek Flash.** DSH ships an experimental "自动授权审查" plugin (`@deepseek-ai/dsh-experimental-auto-review`, row `auto-review`, off by default). Switched on, it adds 自动审查 to the composer's permission menu and reviews every tool call of a session in that mode with one hand-built `llm.stream` request on the session's own model. The plugin now listens on DSH's `llm/stream` waterfall, which every model request passes. It recognizes that request by its fixed `REVIEW_POLICY` system prompt and four-section message, and answers it with the reviewer chosen under Settings → PackyCode → 自动审查 (`autoReviewModel`: `jev-latest` by default, `deepseek-flash`, or `session` to leave it alone). What is reviewed, the policy, asking the user, final denials in children, and refusing a call whose review failed all stay the official plugin's. Every other request goes on untouched. The plugin registers no permission preset and no tool gate of its own.
- **DeepSeek Flash gets the official request itself**, re-addressed to `packycode/deepseek-flash`; the official reviewer reads its answer.
- **jev-latest answers through System One.** Jev cannot write the official JSON answer, so the four sections become its state together with the official policy text, bounded to about 24K characters for its 32K-token per-question limit (Chinese measured one token per character; the user's instructions are kept first). Two questions are asked: the risk (`high` / `medium` / `low`, worded as the official policy and with the conservative option first, because Jev leans to the first choice) and whether the user asked for exactly this action (a `noul` told to judge by effect). A call is allowed when P(low) + P(medium) × P(asked) ≥ 0.6 and P(high) < 0.2. The decision goes back as the official answer, a text block holding `{"risk","decision"}` with a Chinese `reason` naming jev-latest on a denial. A failed review ends the stream with an error, which the official reviewer turns into a refused call. `jev-latest` was answered by `jev-1.14.0`.
- **jev-latest joins the catalog as a classifier, not a chat model.** PackyCode lists it as the `systemone` endpoint (`POST /v1/systemone`) in the `typesafe-officially` group ("jev官方渠道"). DSH's pi-ai adapter only serves chat models, so `PACKYCODE_CLASSIFIER_MODELS` keeps it out of the picker, and the plugin calls it host-side with its own keys. Its group coverage is read like the chat models', and each key's reach line in Settings shows Jev. A review tries the keys in ring order, keys whose groups reach Jev first. An exhausted or rejected key moves aside as on the model route, a key outside the group is passed over, and one gateway 5xx or 429 is resent after 0.5 s.
- **Settings → PackyCode → 自动审查** shows whether DSH's plugin is on (and how to switch it on), the reviewer choice, the reviews the plugin answered since start (allowed / denied / failed) and the last one, and a warning when no stored key's groups reach the chosen reviewer. DSH's own copy under the menu entry still says the same model reviews; the card says which one does. Every review the plugin answers logs one line (`packycode-api: auto review allowed bash (jev-1.14.0, low risk, 352 ms)`), without arguments.
- The web search's key ordering moves to `key-chooser.js` so the reviewer shares it. `scripts/live-check.mjs` sends the official request about one ordinary call and one exfiltration to each reviewer and reads the answers with the official parser (vendored, with the official policy text, in `tests/fixtures/official-auto-review.mjs`).
- Validation, 2026-10-22: 510 offline tests (new: recognizing the official request and passing every other request through; reading its four sections; Jev's bounded state with the official policy, its decision rule and denial reasons; answers and failures read by the official reviewer's own parser; key order, coverage, quota rotation, the transient resend and cancellation; the listener's three choices, the re-addressed Flash request reaching the adapter on its second trip, the counts, status and preference; the `llm/stream` registration; the settings card), both rebuilt bundles and the versioned tarball. One full run failed two hot-install registration tests on their 5-second fixture timeout while the machine was loaded (load average 4.5); they pass alone and in the next full run. Live with a key in `typesafe-officially` and `deepseek-officially`: the official request for 37 scenarios (the 0.2.1-rc.2 policy text and message format, read back by its parser) matched all 35 with a definite answer for both reviewers; jev-latest took a median 0.35 s, DeepSeek Flash 2.3 s. End to end in a scratch DSH 0.2.1-rc.2 headless profile with `@deepseek-ai/dsh-experimental-auto-review` switched on, a session in 自动审查 on `gpt-6.1-sol`, and a request to force-push: with `jev-latest` Jev answered the review (no reasoning, `jev-latest 判定为中风险操作…`); with `deepseek-flash` the request reached `packycode/deepseek-flash`, which gave its own reason; with `session` `gpt-6.1-sol` reviewed it. Each time DSH asked for approval with its own `Auto review denied tool "bash": …` and, without an approval channel, refused the push. `scripts/live-check.mjs` passed every HTTP model, the rotation, the classification and the RPC projections, read the key as reaching `jev-latest`, and both reviewers allowed `pnpm test` and denied an upload of `~/.ssh/id_rsa`. Not yet checked in the desktop app.

- **GPT web search works again.** With the GPT backend, every search failed with "PackyCode search returned no web_search_call". (`rate_limit_exceeded`) and its `server_error` inside the 200 stream, before any output, so the gateway cannot resend them itself. The search resends on the same key after the pause the message names (1 s when it names none; a pause over 5 s is reported instead), at most twice, as the official Codex client resends them. Quota and key wording are never resent, and no key is moved aside for this. When it persists, the error names the model and suggests the DeepSeek backend. Any other failure relayed in the stream is reported at once as "failed upstream", not as HTTP 200.
- **Every GPT search sends a `prompt_cache_key`.** The Codex group answers a Responses request without one with a 403 ("请使用标准 Codex 客户端"; 3 of 3 live, while 3 of 3 with one were accepted). DSH's searches already carried the session id or the plugin's fallback id; a caller that names no session, such as `scripts/live-check.mjs --with-search`, now gets one id per provider, as the model route does.

## 1.3.5

- **An outdated Claude Code CLI is caught before the request, and the CLI card updates it.** 1.3.4 always passes `--permission-prompts none`, which Claude Code added in 2.1.259 (2026-09-02). A colleague's CLI from the official installer was 2.1.223 (2026-08-05): it rejected the option at start-up, every `cc` Claude turn failed with "the installed Claude Code CLI is too old", and the card still showed it as installed. The plugin now requires 2.1.259 or later. An older detected CLI is refused before it is started, with the detected and required versions; a cached detection that looks outdated is probed again first, so a CLI updated in a terminal is used at once. The card marks such a CLI **too old** and offers **Update Claude Code CLI**. A CLI from the official installer (or any install that is not npm's) is updated with `claude update`, run with the plugin's own CLI home and without the user's `ANTHROPIC_*` / `CLAUDE_*` / `DISABLE_*` variables. An npm global install is updated by npm itself — the npm beside the CLI, which owns its prefix — with `npm install -g @anthropic-ai/claude-code@latest --allow-scripts=@anthropic-ai/claude-code`. The update succeeds only when the CLI detected afterwards is new enough; otherwise the card says whether it stayed old (for example a Homebrew install), stopped running, or could not download, with the command's output. The CLI's flags and environment for requests are unchanged.
- **The npm install allows Claude Code's install script.** npm 12 skips install scripts unless they are allowed, and `@anthropic-ai/claude-code` places its native binary in its postinstall, so the one-click `npm install -g @anthropic-ai/claude-code` left a CLI that only printed "claude native binary not installed". The install now passes `--allow-scripts=@anthropic-ai/claude-code`, as do the commands the card and error messages suggest; npm 10.9.9 and 11.21.1 accept the option and install a working CLI. `claude update` on an npm install has the same problem on npm 12 (it reported success from 2.1.223 to 2.1.303 and left no binary), which is why npm installs are updated through npm.
- **The Claude route can no longer be chosen.** The key's groups alone decide: a key in `cc` always sends Claude requests through the official CLI, and every other group uses HTTP. The CLI card's "By group / Always CLI / Always HTTP" switch, the `claudeTransport` setting and its RPC are removed; a value left in a profile is ignored. Pinning HTTP sent a `cc` key's requests where the gateway refuses them as a third-party client, and pinning the CLI made other keys need one.

## 1.3.4

- **Keys in `cc` send Claude requests through the official Claude Code CLI again; `cc-sale`, `cc-expensive`, `claude-officially` and every other group keep the native HTTP route.** PackyCode's `cc` group only serves the official client, so the route now reads the request key's groups and hands those Claude requests to this device's Claude Code CLI. The delisted `claude-sale` group is not included until it returns. Unlike the 1.2 delegation, the CLI is only the transport: it runs with all of its own tools disabled, DSH's system prompt appended to its own, and DSH's tools for the turn listed through a per-process MCP bridge on 127.0.0.1 as `mcp__dsh__<name>`. Every call the model makes is executed by DSH — permissions, sandbox, plan mode and its review, questions, todos, subagents, image generation and tool cards are the same as over HTTP — and the result answers the call the CLI is holding open. The request itself is built once for both routes (DSH history, attachments, signed thinking and tool schemas through pi-ai), and the CLI's raw stream events come back as the same Anthropic SSE stream, so usage, replay, error classification and key rotation are unchanged.
- **One live CLI process per conversation.** A DSH session keeps one CLI process per model: the next step's tool results and the user's next turn continue it, so its requests share one cacheable prefix. A request that does not continue it (compaction, a plan-mode switch, another key or effort) gets a process resumed from DSH's own history through a CLI transcript; a mid-turn resume uses the CLI's interrupted-turn continuation. Session titles and compaction run in one-shot processes. Idle processes stop after 20 minutes, at most eight stay alive, and all stop when the plugin unloads.
- **The CLI is isolated and adds no behavior of its own.** It runs with its own config home (`~/.dsh/packycode-claude-cli`), no user/project settings, CLAUDE.md, auto-memory, slash commands, session persistence, auto-update or telemetry, and with inherited `ANTHROPIC_*` / `CLAUDE_*` variables removed. Only the plugin's selected key reaches it, as `ANTHROPIC_AUTH_TOKEN`. Its own retries, model and refusal fallbacks and compaction are off: one DSH step is one API request and retries follow DSH's policy. MCP idle timeouts and auto-backgrounding are disabled so a call can wait on a user's approval or plan review (a 400-second hold was verified).
- **Settings → PackyCode → Claude Code CLI** is back: install status and version, a one-click npm install, the live-process counters, and the Claude route — by group (default), always CLI, or always HTTP. Every key that reaches Claude shows which route its Claude requests take. `claudeTransport` and `claudeCliPath` are volatile settings; the 1.2 `claudeCliMode` / `claudeCliCwd` and the `claude_code` delegation tool stay removed.
- **CLI failures say what to do, once.** A missing CLI, a broken launcher or an outdated CLI that rejects an option are explained without a status code, so DSH does not retry them twenty times. A request the official CLI sent that the gateway still refuses as a client anomaly gets its own explanation with the gateway's words; quota and invalid-key failures relayed by the CLI rotate keys exactly as over HTTP. Nothing ever switches route or provider by itself.
- Validation, 2026-10-17: the real Claude Code CLI 2.1.295 was probed against a local gateway for every flag and behavior relied on (MCP `_meta` tool-use ids, sequential held calls, `--resume <file>`, interrupted-turn resume, stream-json events with signature deltas, error reporting, retries off). Live with a `cc` key through the CLI: Opus, Sonnet and Haiku each passed text, a native tool roundtrip continuing the same process, image input, a Chinese title and plan mode (inventory lookup → `exit_plan_mode` → approval) — 15 of 15 checks. The full plugin wiring in `auto` read the key's groups (`cc`, …), routed Claude through the CLI and passed Haiku and Sonnet tool roundtrips; the same key pinned to HTTP still passed. Offline: tests for the route policy, transcript, tool names, MCP bridge, process lifecycle through a protocol-faithful fake CLI, plugin wiring and the settings card.
- **Back-to-back releases no longer hold `latest` back.** The promote job only looked at the version `next` names, so a release published before the previous one was 25 hours old reset the wait, and a day of iteration left `latest` where it was. It now promotes the newest version after `latest`, up to `next`, that has aged 25 hours, so `latest` trails the newest release by about a day. A version deprecated on npm is never promoted, which is how a broken release is held back. AGENTS.md gains a "Staged releases" section so anyone iterating knows releases go through `next` and must not be published or moved to `latest` by hand.
- **DSH 0.2.1 (pi-ai 1.1.0) compatibility.** DSH 0.2.1 asks the route for a key before it lists models, and lists none without one. That question now only checks the ring for a usable key: with two or more keys, listing no longer waits up to six seconds for the first group reading (which held up DSH's whole model catalog, since it lists every provider together) and no longer sends the group probes. pi-ai 1.1.0 also hands the provider a transcript whose system message declares the offered tools as `toolsAdded` instead of `context.tools`, so the one-time replay of the gateway's captured Haiku/Sonnet client-anomaly and test-message refusals stopped recognizing a first tool request; it recognizes both shapes again. Without a usable key DSH 0.2.1 shows no PackyCode models; adding, removing or auto-disabling a key refreshes its model list through DSH's credential-record event. Live on 2026-10-17 against the packages DeepSeek Harness 0.2.1-rc.2 ships, its patched pi-ai included: `scripts/live-check.mjs` passed for all ten models (Claude over HTTP), key rotation and the RPC projections, and `scripts/claude-check.mjs --transport cli` passed all 15 checks (text, tool, image, title and plan on Opus, Sonnet and Haiku).
- **The plugin declares and is tested on the DSH 0.2.1 host.** The peer ranges add `@deepseek-ai/cordis` 4.0.5 and `@earendil-works/pi-ai` 1.1.0, and `compatibility.json` records 0.2.1-rc.2 as the latest tested host. The development dependencies are now the packages DeepSeek Harness 0.2.1-rc.2 ships (dsh-* 0.2.1-rc.2, cordis 4.0.5, schemastery 3.18.5, pi-ai 1.1.0); the connection and chat-image tests also run on 0.2.0-rc.2 through the host fixture, and their DSH 0.1.5 rows are gone. Tests that call the provider directly now hand it the context pi-ai's own `Models` would, and the host fixtures follow 0.2.1's PTC runtime, browser-auth and Chat bundle changes.
- Validation, 2026-10-17: 456 offline tests on the DSH 0.2.1-rc.2 packages (0.2.0-rc.2 through the host fixture), both rebuilt bundles and the versioned tarball; the same suite also passed against the packages extracted from the desktop app. Live through the built route on those packages: `scripts/live-check.mjs` for all ten models, key rotation and the RPC projections, and `scripts/claude-check.mjs --transport cli` with a `cc` key, 15 of 15. - **Balance on mainland networks.** The default balance host is now `https://www.packyapi.ai` (PackyAPI's current site). `www.packyapi.com`, the default through 1.0.4, is DNS-poisoned on mainland networks: every public resolver checked (AliDNS, DNSPod, 1.1.1.1, 8.8.8.8, even AliDNS over HTTPS) returned an unrelated foreign IP, and a direct Node fetch failed with `ECONNREFUSED`. Without a proxy every key read `fetch failed` from it, which is what a Windows user saw. With a proxy it worked, so the failure came and went. A profile that saved the old host keeps it as a fallback, but `.ai` is tried first. Verified live without a proxy: `.ai` answers in about 1.3 s.
- A failed balance read keeps each key's last good balance (and the last account figures), marked `stale` with the time of that read and this read's error. Settings shows a note, and the composer shows `≈US$…`. These values stay in the host process: a page refresh keeps them and a restart clears them. A transport failure now names its cause (`fetch failed (ENOTFOUND)`, `no answer within 20s`), and a 429 says the gateway is rate limiting. The composer says "余额读取失败" instead of "无可用 Key" when a usable key's read failed. The total limit shows `—` instead of "不限额度" when no key was read.
- **Claude Code CLI identity.** In `-p` mode the official CLI picks its identity line from whether it got appended instructions. With them, it tells the model "You are Claude Code, Anthropic's official CLI for Claude, running within the Claude Agent SDK."; without them, "You are a Claude agent, built on Anthropic's Claude Agent SDK." A delegated turn ran without them and was refused upstream with `403 Request blocked: this endpoint only accepts requests from the official Claude Code CLI`. Every run now passes `--append-system-prompt`: the delegation instructions (moved out of the prompt) or, for the `claude_code` tool, a short delegation note. This is the binary's own selection (read from its code and confirmed by capturing its request); the plugin does not rewrite the CLI's system prompt. That wording is also recognised as a client-policy refusal, explained without the bare 403, and never disables a key.
- **Prompt over stdin; images in CLI turns.** The CLI now reads its input from stdin instead of argv. A streaming turn sends one `stream-json` user message, the `claude_code` tool sends plain text, and stdin is closed afterwards. A Windows command line is capped near 32K characters and cannot carry an image. Images in a CLI-backed turn used to become the text `[图片]`; they are now read from the attachment store at the HTTP route's request size (2048×2048, about 1 MiB), sent as Anthropic image blocks where they appeared, and labelled with their read-only host copy. A turn carries at most 20 images and 20 MiB of base64, dropping the oldest first. An image left out, or unreadable, is described with its path instead of failing the turn. Uploaded files are named with their host copy, and structured tool results keep their text. Verified with the real CLI 2.1.295 against a local gateway: the image reached `/v1/messages` as a base64 image block.
- **No more silent CLI waits.** A delegated turn now opens its reasoning block with `▸ 启动 Claude Code CLI…`, shows the CLI's version and model once it is up, and shows each retry the CLI makes on its own (`↻ 网关返回 HTTP 503（server_error），CLI 自动重试 1/10，1.0 秒后`). Before, a gateway answering `503 packy_concurrency_queue_full` (账号并发排队已满) or 429 kept the CLI retrying for minutes with nothing on screen. When the retries run out, the turn says PackyCode's Claude upstream is busy and how many retries were made, keeping the gateway's words and request id. A streaming CLI that prints nothing within 2 minutes of starting is stopped and reported with its stderr tail. Verified with the real CLI against a local gateway that answers 503, both recovering after two retries and giving up.

## 1.0.0

First release.

- Ships a self-contained `packycode` LLM route: the plugin builds its own pi-ai provider, model catalog, retry policy, key ring, and balance reader, and registers them through `llm.registerAdapter`. Installing the package is the whole setup.
- Built-in catalog: `deepseek-flash` (openai-completions), `gpt-6.1-sol` (openai-responses), `claude-opus-5-5` (anthropic-messages), each pinned to the protocol and base URL the gateway serves and carrying the vendor's documented effort levels.
- Multiple API keys in one credential record, used in order. A key the gateway exhausts (`额度/余额/insufficient quota`) or rejects (401 / `无效的令牌`) is marked disabled and the active pointer moves to the next usable key, so the harness retry of the failed step resolves a different key.
- Route retry policy retries `QUOTA`, `AUTH`, and `INVALID_REQUEST` in addition to the defaults: the first two make rotation reachable, the last absorbs this gateway's misleading 400 when an upstream channel is dead.
- A Responses request without a `prompt_cache_key` is refused by the gateway's Codex-group check with 403. The harness supplies a session id; the plugin adds a per-process fallback when a caller does not.
- Balance display: the settings section lists every key with its available/used quota, reset period, and state; the composer shows the active key's remaining balance. Reads come from `/api/usage/token/` with a host fallback, plus the account's `/v1/dashboard/billing/*` pair.
- Validation: 39 offline tests (key ring, balance parsing and fallback, failure classification, catalog contract, stream guard, `apply()` wiring with and without a connection service, and the real `PiAiAdapter` resolving every advertised model and preparing its call). `scripts/live-check.mjs` verified against the live gateway: balance read, one answer from each of the three models, a rotation rehearsal with an invalid key in front of the real one, and the host adapter classifying the rejected key as `AUTH`.
- The plugin injects only `llm` and `credentials`; the browser RPC surface is requested through `ctx.inject(['connection', 'webServer'], …)`. An isolated end-to-end boot (headless profile in a scratch `DSH_HOME`) proved this matters: with `connection` in the inject list the entry stayed pending and the boot failed, and without it the same boot answered through `packycode/gpt-6.1-sol`.
- Default key names no longer collide after a removal: the ring shrinks when a key is deleted, so `Key N` numbering follows the highest name in use instead of the key count (removing the first of two keys and adding another used to produce a second "Key 2").
- The balance card lists one row per key/account (PackyCode token name, remaining, used, limit, reset period, active/disabled state), and the key rows show only the label plus that same account name so the two line up; the site-wide account total moved to a summary line. The account read now walks past a key the gateway rejects instead of letting whichever key sits first blank the total.
- The package also ships an entry patch for the `connection` row: `inject: [credentials, webRuntime, webServer]`. Connection registers a channel through `owner.webServer` read on *its own row's fiber*, so the shipped `dsh-web-app` row (which injects `webRuntime` alone) made every browser call answer HTTP 405 while the boot log stayed clean. Verified in a scratch web profile over the real HTTP transport: `POST /packycode-api/status` moved from 405 to 401 (registered, unauthorized), and with the root token exchanged for its cookie `status`, `keys/add`, and `balance` all returned their projections — including a live per-key balance and account total, with no key material in any response.
- `claude-sonnet-5-5` and `claude-haiku-5-5` join the catalog, CLI-backed like `claude-opus-5-5`. A session-title request (`purpose: 'session-title'`) on any CLI-backed model now runs on `claude-haiku-5-5`, read-only, in a temp directory (so no project memory is loaded), with the title instructions passed as `--append-system-prompt` and only the request text as the prompt — instead of a full Opus delegated turn in the workspace for every new session.
- The settings section now has a **Claude Code CLI** card: it detects whether this device has the CLI and shows its version (`claude --version`, run in the plugin's isolated config home) and location; without one it warns that the Claude Opus model cannot work and offers an **Install** button that runs `npm install -g @anthropic-ai/claude-code` on the host — the same command on macOS and Windows. The install starts over `claude-cli/install` and the panel polls `claude-cli/status`, so no request is held open for minutes; failures are classified (`npm-missing`, `permission`, `network`, `timeout`, `not-found-after-install`) with npm's last output lines. Lookup covers the official installer, npm/Homebrew/Volta/nvm locations, `%APPDATA%\npm` on Windows, PATH with each platform's rules (Windows `Path`, quoted entries), and finally `npm prefix -g`, because a GUI-launched host's PATH is usually shorter than a terminal's. The runner resolves the CLI per run, so a CLI installed after startup is used without a restart, and puts the CLI's directory on the child's PATH so an npm launcher's `env node` resolves. On Windows an npm `claude.cmd` launcher is never run through `cmd.exe` (Node requires a shell for `.cmd`, which would make `cmd.exe` parse the prompt): the runner reads the launcher and starts the program it forwards to (`node …\cli.js` or a packaged `.exe`) directly. A turn whose CLI is missing now says so and points to the install button instead of `spawn claude ENOENT`.
- The Claude Code CLI's mode now follows the session's own permission preset by default (`claudeCliMode: auto`), so installing the plugin needs no profile patch: `read-only` → `read-only`, `workspace-write` → `edit`, `danger-full-access` with approval `never` → `full`. The CLI cannot ask the harness user for approval, so a session that still asks never gets `full`. The `claude_code` tool's `mode` argument is capped at the same ceiling, and an explicit `read-only`/`edit`/`full` setting still pins the mode. Read through `ctx.get('sandboxPolicy')` and `ctx.get('approval')`; without either service the previous `edit` default stands.
- A CLI-backed `claude-opus-5-5` turn now shows its work live: the CLI's thinking and every tool call it makes (`▸ Bash · git status`, `▸ Read · …`, plus `✗ …` when a tool fails) stream into a reasoning block while it runs, and its answer streams as text, each run bracketed by `block-start`/`block-end` as the harness stream grammar requires. Before, only answer text was forwarded, so a turn spent in the CLI's own tool loop showed nothing until the end.
- A CLI-backed turn's usage now carries cache traffic. The CLI's requests are almost entirely cache hits (`input_tokens: 2`, `cache_read_input_tokens: 42880`), and only `input_tokens` was forwarded, so the session showed a 0% cache hit rate and a context of a few tokens. The prompt side now comes from the CLI's **last** request (uncached input, cache read, cache write) — the harness reads it as context occupancy, which a sum over a multi-step CLI turn would overstate — and output is the CLI's whole-turn total.
- The CLI's stdout and stderr are decoded as UTF-8 on the stream instead of chunk by chunk, so a multi-byte character (Chinese text, emoji) that straddles two pipe reads no longer turns into `�` in the answer, the live reasoning, or a failure message; the same applies to `npm` and `claude --version` output. A consumer that stops reading a streaming CLI turn early now stops the CLI instead of leaving it running until its 30-minute timeout.
- `claude-opus-5-5` is now served by the **local official Claude Code CLI**: selecting that model runs the CLI per turn instead of an HTTP request, which is the only client PackyCode's `cc` group serves Claude models to. The route dispatches per model, so `deepseek-flash` and `gpt-6.1-sol` keep the pi-ai path. A delegated turn drops the harness system prompt and tool schemas (the CLI brings its own), renders the recent conversation into the CLI prompt, and streams the CLI's text back as harness chunks. New settings: `claudeCliPath`, `claudeCliMode` (`read-only`/`edit`/`full`, default `edit`), `claudeCliCwd` (empty = the session's workspace, resolved through the `agents` service). Verified live through the plugin's own adapter: `claude-opus-5-5` → `finish=stop`, `adapter-cli-ok`, 3s, while the HTTP-backed models kept answering.
- New `claude_code` tool: a delegated task is run by the **local official Claude Code CLI**, which is the only client PackyCode's `cc` group serves its Claude models to. The child process receives this plugin's endpoint and API key plus an isolated `CLAUDE_CONFIG_DIR` — required because `~/.claude/settings.json` env overrides an inherited environment, so without it the user's own CLI configuration would silently win. `mode` bounds the CLI's own tools (`read-only` / `edit` / `full`). Verified live through the plugin's runner against the real CLI and gateway: `cli-bridge-ok`, 4s, $0.1984; and offline by a stub-CLI test that asserts the argv, environment isolation, session-workspace cwd, and rendered result. Unlike a forged client identity this runs the genuine binary, so the group's requirement is met rather than bypassed; the trade-offs (per-call cost, tens-of-seconds latency, and the CLI's own tools running outside the harness's sandbox and transcript) are documented in the README.
- A gateway group that serves only the vendor's official client (for example PackyCode's `cc` group answering `403 This API endpoint is only accessible via the official Claude CLI`) is now recognised as a client-policy refusal: the plugin does not retry it, does not disable or rotate a key, and replaces the bare 403 — which the harness renders as an invalid-API-key problem — with a sentence naming the real cause and the groups that do serve API clients. Verified live: the harness receives `PI_AI_ERROR` (outside the route's retryable codes) with no key rotated, while `deepseek-flash` and `gpt-6.1-sol` keep answering.
- The balance card's headline figures are now the **sum of the listed keys** (remaining, used, limit) instead of PackyCode's account-level billing numbers, which count every token on the account and read as a wrong total when several keys are stored. Keys whose read failed are excluded and reported in a note; a key with no quota limit marks the total as unlimited rather than inflating a limit. The account-level numbers remain, on their own clearly-labelled line. Verified in a real browser against the app's own 0.2.0 runtime with two keys: `合计剩余 US$999.07 · 合计已用 US$0.93 · 合计额度 US$1,000.00`, with the account line reading `PackyCode 账号（含同账号其它用量）：剩余 US$407.00 · 已用 US$93.00 · 额度 US$500.00`.
- The route retries up to 20 times (was 3) for every model it serves. One route carries all three models, so the budget is shared: this gateway drops an upstream channel or key per request, and the retry is also what reaches the next key. With the default backoff (500 ms doubling, capped at 10 s, 10% jitter) a failure is surfaced after roughly three minutes of retrying instead of about seven seconds.
- The browser half sets a default `payload` on every channel call. Connection's request envelope requires the field, and `JSON.stringify` drops an `undefined` one, so `call('status')` was refused with `invalid client-request message` and the settings panel showed a read failure. Reproduced in a real browser against the app's own 0.2.0 runtime (`payload` omitted → rejected, `payload: {}` → accepted) and verified fixed there: opening Settings → PackyCode, pasting a key, and clicking Add now renders the account row (`战魂銘人-张洋凡 · 使用中 · 剩余 US$499.07 · 已用 US$0.93 · 额度 US$500.00 · 每月`), the account totals, and the key row with its matching account name.
- Client styling no longer fills a button with `--dsw-alias-brand-primary` while writing its label in `--dsw-alias-label-inverse`: on this theme the brand colour is light and the inverse token is absent, so the Add button rendered as an empty box. Emphasis is now border-and-weight only, the active-key chip keeps the readable label colour, and the host-override inputs are disabled when the runtime cannot write settings.
