# Changelog

## 1.1.2

- **Claude CLI follows DSH plan mode.** While the current session's plan mode is on (including a selection that applies on this step but is not logged yet), a Claude model turn and the `claude_code` tool run the local CLI with `--permission-mode plan`. That wins over the session permission preset and over an explicit `claudeCliMode` pin. The CLI may explore read-only; other permission prompts are denied, and after eight denials the run stops instead of hanging. `ExitPlanMode` is never allowed inside the CLI process. A submitted plan becomes the assistant's `exit_plan_mode` tool call, so DSH's existing review approves it and the next step implements. The delegation tool returns the plan text for the parent model to submit. Session titles stay read-only. A host without the plan-mode service behaves as before.

## 1.1.1

- **Claude CLI search through MCP.** CLI-backed Claude turns and the `claude_code` delegation tool now get a temporary, authenticated, loopback HTTP MCP `web_search` tool calling the plugin's selected DeepSeek/GPT backend. Native CLI `WebSearch` is explicitly denied in every permission mode: it makes a separate Claude server-tool request that PackyCode can refuse even when ordinary turns work. The official CLI/system identity is preserved; no vendor headers or identities are forged. Backend selection applies to CLI searches even when DSH routing is set to Off/Do not take over; the DSH routing mode remains independent, and headless profiles need no `web` service. MCP callbacks capture their originating session ID before losing agent context and always call the direct PackyCode provider, never an auto-router fallback.
- **Bridge boundaries.** Each run has a collision-resistant server/tool name, an independent random capability, and an owner-only temporary MCP config; search API keys stay in the host key ring, not MCP config, argv or results. Only the exact search tool is added to read-only/edit auto-approvals; shell/file privileges, existing MCP configuration, and user/managed deny rules remain unchanged. No `--strict-mcp-config` or wildcard MCP approval. Queries are bounded at 2000 characters, bodies at 16 KiB, sources at 8, concurrency at 2, calls at 8 per run, and each logical search at 60 seconds including retries/key resolution. Tool failures are explicit, sanitized errors, with no automatic backend/native-search fallback. Results are marked as untrusted external content.
- **Lifetime and redaction fixes.** MCP capability is revoked immediately on cancellation, including while binding/writing config; late filesystem resources remain owned until cleanup completes. Normal/error exits, spawn/stdin failures, startup watchdog, timeout, early iterator close, and plugin unload clean up. Fixed pre-existing runner races where cancellation during credential/binary setup could still spawn a child and returning at the first labeled-key yield left a child running. Streaming now checks nonzero process exits even after a successful-looking result. Redaction handles JSON-escaped keys and credentials/capabilities fragmented across text/thinking deltas. Title generation allocates no MCP server/search grant.
- The settings card explains CLI backend selection versus DSH routing. Added `scripts/cli-search-check.mjs`: real official CLI + a local mocked Claude gateway verifies actual MCP transport/permissions and absence of native search in all modes; `--live --backend deepseek|gpt` performs one real search through that backend. The mock gateway is a test fixture only, never a replacement for DSH or the production gateway.
- Validation: complete suite on Node 24 and Node 22.20.0; real CLI 2.1.39 and 2.1.295 both called the built bridge in read-only/edit/full modes, with official identity retained and no Claude native-search child call. Real DeepSeek and GPT searches via the bridge returned 10 and 20 sources; one initial GPT backend attempt failed explicitly, and a later attempt succeeded. Ordinary HTTP models, key rotation/failure classification and secret-free RPC projections passed the live check. Claude main-model responses in the MCP test were mocked (the available stored key has no Claude group); actual Claude upstream/desktop DSH integration is not claimed from these checks.

## 1.1.0

- **Keys are chosen by their groups.** A colleague's Claude turns kept failing with "PackyCode 的上游拒绝了这次 Claude Code CLI 请求……请更新 CLI" because the active key had no Claude Code group; PackyCode answers such a key with the same "only the official Claude Code CLI" wording as a real client fault. The plugin now reads each key's groups and routes by them:
  - A new group reader asks the gateway itself: a request for a model id no gateway routes (`dsh-packycode-group-probe`, `max_tokens: 1`) is refused before any upstream call with the token's groups (`已选分组=[codex deepseek-officially kimi-sale]`), nothing is billed. `/v1/models` adds the key's reachable models, and the public `/api/pricing` maps each catalog model to its groups (`claude-opus-5-5`: `cc` / `cc-expensive` / `cc-sale` / `claude-officially`; `claude-haiku-5-5` only `cc` and `claude-officially`) and gives each group's description. Pricing and every key are read concurrently, 4 keys at a time; the two per-key requests are independent evidence, and a key the gateway rejects (401 / 无效的令牌) counts as reaching nothing. Readings are cached 10 minutes, keep the last good groups when a read fails (marked stale), and never carry key material.
  - When the reading shows the active key cannot reach a request's model and another stored key can, that request runs on that key, on all three paths: HTTP models (the stream wrapper swaps the resolved key per model), Claude CLI runs (`resolveCredential({ model })`), and web search (candidates ordered by coverage). The active pointer does not move, a key is passed over only on evidence, and with no better key the active one is used. A request with two or more usable keys waits at most 6 s for the first reading.
  - Every Claude CLI turn names its key in the reasoning (`▸ 使用 Key「cc」（分组：cc）`, or `当前 Key「A」的分组不能用 claude-opus-5-5，本轮改用 Key「B」`, or a warning that no stored key has a Claude group) — by label only.
  - A CLI refusal from a key without a Claude group — the 403 official-CLI wording or the 400 `当前令牌未覆盖供应商` — is explained as that: the key, its groups, the groups the model needs, and that the CLI does not need updating. The 400 names the groups itself; for the 403, a fresh reading is consulted when the run started before the groups were known. Status tokens are kept out of the sentence so no retry is spent on it. A key that does have a Claude group keeps the CLI explanation, now naming the key.
  - New RPC endpoint `groups`; the reading is dropped when keys are added or removed or the hosts change.
  - The key switch itself already applied per run: reproduced with the real CLI 2.1.39 against a capture gateway through the plugin's own wiring, the turn after **切到此 Key** sent the new key. A restart only appeared to fix it.
- **Settings panel redesign.** The balance list and the key list showed the same keys twice; one **账户与 Key** card now has the totals as tiles, then one row per key with its balance, a usage bar, its groups (hover for the description), a ✓ / ◐ / ✕ line per model family, and its actions. Web search uses segmented controls with the selected option's hint; the CLI card shows a status dot and a warning callout when the CLI is missing; the version card is one row. The stylesheet uses only host design tokens (`settings-card-fill/stroke`, `radius-*`, layer-1 inputs, primary/outline/danger buttons) so it follows light and dark themes; it referenced two tokens the host never defined (`--dsw-alias-border-default`, `--dsw-alias-state-warning-primary`) and painted cards, rows, buttons, and inputs the same grey. Copy and styles moved to `client-copy.js` and `client-style.js`; both languages carry the same keys, and English no longer shows full-width punctuation. Checked in a harness rendering the built bundle with DSH 0.2.0-rc.2's theme CSS, in both themes and languages.
- **Refactor.** `index.js` went from 714 to about 330 lines of composition: the HTTP route moved to `route.js`, key choice and rotation to `key-chooser.js`, the `claude_code` tool to `claude-tool.js`, both settings generations to `preferences.js`, and the profile-patch locator (patch path, base config, HMR transaction) next to the composition. The balance, group, and version readers share one cached single-flight reader (`cached-read.js`), and every host-side request goes through one bounded fetch (`request.js`: timeout plus caller signal, redirects refused, transport errors named). The balance reader now resolves fetch at call time like the others. Host helpers live in `hosts.js`; the coverage wording is shared from `failures.js`; test doubles live in `tests/helpers.mjs`. `scripts/live-check.mjs` now drives the plugin's own route composition instead of a hand-built copy, reports groups, separates the group pass-over from the rotation rehearsal, and takes `--with-search`. Public exports are unchanged apart from additions.
- `compatibility.json`: the 0.2.0-rc.2 note claimed `settings.installSection` exists on that line; it does not (its settings service only writes volatile fields), so host overrides are read-only there.
- Verified live through the built bundle: groups `codex, deepseek-officially, kimi-sale` with Claude unreachable; `deepseek-flash`, `gpt-6.1-sol`, and `gpt-6-astra` answered through the registered route; an invalid key in front was passed over with group evidence and disabled by rotation without; a Claude turn through the real CLI 2.1.295 with a key lacking a Claude group opened with the no-Claude-group warning and ended with the group explanation; both search backends answered. A full group reading took about 1 s (it took 15 s sequentially while `cf.api.fan` was resetting connections).

- **Web search through PackyCode.** The plugin registers two providers with DSH's `web` service: `packycode-api` searches through PackyCode for every request, and `packycode-api-auto` does so only for sessions running on a PackyCode model, handing every other request to the search provider the web row named before. **Settings → PackyCode → Web search** picks the routing (do not take over — the default — / auto / always) and the backend:
  - `deepseek` (default): `deepseek-flash` over Anthropic Messages at `/v1/messages` with the `web_search_20250305` server tool, `max_uses` 3. Results come from `web_search_tool_result` blocks.
  - `gpt`: `gpt-6.1-sol` over Responses at `/v1/responses` with the hosted `web_search` tool (`tool_choice: required`, `reasoning.effort: low`, list input, `prompt_cache_key`). Results come from `url_citation` annotations and the `web_search_call` actions.
  - Both return the model's summary as `content`, with sources deduplicated by URL. A search uses only this plugin's ring keys, is bounded at 55 s, and refuses redirects. An exhausted or rejected key moves aside through the same sink as the model route and the next key is tried. A `model_not_found` / `当前令牌未覆盖供应商` refusal skips to the next key without disabling one, and finally says which backend to switch to. Gateway text is masked so a key never appears in an error.
- **How DSH reaches the providers.** Auto and Always maintain one marked `- id: web` entry in the running profile's `cordis.patch.yml` (`profileContext.patchPath`, or the owning profile found from the install), which DSH hot-applies. The entry is rewritten in place, written only when it changes, restates the web row's other scalar fields (a profile patch replaces the whole config), and records the base provider it replaced as `# fallback: …`. The runtime slot is never written: the Codex and Kimi subscription plugins rewrite it on every web restart, and their routers already fall back to the web row's base. A request that loops back to the auto provider from another router goes to `deepseek-official`. Writes run inside DSH's HMR transaction when one is free and unlocked when DSH refuses to nest it. Removing the entry (the default routing) leaves the rest of the file byte for byte.
- The preference is two new Config fields, `searchProvider` and `searchBackend`. On DSH 0.2 they are volatile fields written through `settings.update('packycode-api', …)` and followed through `loader/volatile-update`; the generated duplicate settings page is hidden. On DSH 0.1.5 they live in the installed settings section. New RPC endpoints `search/status` and `search/update` return only the preference, what is in effect, and whether Codex or Kimi routers are present.
- Verified live through the built bundle against `cf.api.fan`: the DeepSeek backend returned 10 sources in 5.4 s and the GPT backend 20 sources in 14.2 s for one query, with no key disabled. During the same session the gateway refused GPT requests from this key for a while as `当前令牌未覆盖供应商 "OpenAI"` and then served them again. Not yet exercised in a running DSH desktop session.

## 1.0.5

- **Balance on mainland networks.** The default balance host is now `https://www.packyapi.ai` (PackyAPI's current site). `www.packyapi.com`, the default through 1.0.4, is DNS-poisoned on mainland networks: every public resolver checked (AliDNS, DNSPod, 1.1.1.1, 8.8.8.8, even AliDNS over HTTPS) returned an unrelated foreign IP, and a direct Node fetch failed with `ECONNREFUSED`. Without a proxy every key read `fetch failed` from it, which is what a Windows user saw. With a proxy it worked, so the failure came and went. A profile that saved the old host keeps it as a fallback, but `.ai` is tried first. Verified live without a proxy: `.ai` answers in about 1.3 s.
- A failed balance read keeps each key's last good balance (and the last account figures), marked `stale` with the time of that read and this read's error. Settings shows a note, and the composer shows `≈US$…`. These values stay in the host process: a page refresh keeps them and a restart clears them. A transport failure now names its cause (`fetch failed (ENOTFOUND)`, `no answer within 20s`), and a 429 says the gateway is rate limiting. The composer says "余额读取失败" instead of "无可用 Key" when a usable key's read failed. The total limit shows `—` instead of "不限额度" when no key was read.
- **Claude Code CLI identity.** In `-p` mode the official CLI picks its identity line from whether it got appended instructions. With them, it tells the model "You are Claude Code, Anthropic's official CLI for Claude, running within the Claude Agent SDK."; without them, "You are a Claude agent, built on Anthropic's Claude Agent SDK." A delegated turn ran without them and was refused upstream with `403 Request blocked: this endpoint only accepts requests from the official Claude Code CLI`. Every run now passes `--append-system-prompt`: the delegation instructions (moved out of the prompt) or, for the `claude_code` tool, a short delegation note. This is the binary's own selection (read from its code and confirmed by capturing its request); the plugin does not rewrite the CLI's system prompt. That wording is also recognised as a client-policy refusal, explained without the bare 403, and never disables a key.
- **Prompt over stdin; images in CLI turns.** The CLI now reads its input from stdin instead of argv. A streaming turn sends one `stream-json` user message, the `claude_code` tool sends plain text, and stdin is closed afterwards. A Windows command line is capped near 32K characters and cannot carry an image. Images in a CLI-backed turn used to become the text `[图片]`; they are now read from the attachment store at the HTTP route's request size (2048×2048, about 1 MiB), sent as Anthropic image blocks where they appeared, and labelled with their read-only host copy. A turn carries at most 20 images and 20 MiB of base64, dropping the oldest first. An image left out, or unreadable, is described with its path instead of failing the turn. Uploaded files are named with their host copy, and structured tool results keep their text. Verified with the real CLI 2.1.295 against a local gateway: the image reached `/v1/messages` as a base64 image block.
- **No more silent CLI waits.** A delegated turn now opens its reasoning block with `▸ 启动 Claude Code CLI…`, shows the CLI's version and model once it is up, and shows each retry the CLI makes on its own (`↻ 网关返回 HTTP 503（server_error），CLI 自动重试 1/10，1.0 秒后`). Before, a gateway answering `503 packy_concurrency_queue_full` (账号并发排队已满) or 429 kept the CLI retrying for minutes with nothing on screen. When the retries run out, the turn says PackyCode's Claude upstream is busy and how many retries were made, keeping the gateway's words and request id. A streaming CLI that prints nothing within 2 minutes of starting is stopped and reported with its stderr tail. Verified with the real CLI against a local gateway that answers 503, both recovering after two retries and giving up.

## 1.0.0

First release.

- Ships a self-contained `packycode` LLM route: the plugin builds its own pi-ai provider, model catalog, retry policy, key ring, and balance reader, and registers them through `llm.registerAdapter`. Installing the package is the whole setup.
- Built-in catalog: `deepseek-flash` (openai-completions), `gpt-6.1-sol` (openai-responses), `claude-opus-5-5` (anthropic-messages), each pinned to the protocol and base URL the gateway serves and carrying the vendor's documented effort levels.
- Multiple API keys in one credential record, used in order. A key the gateway exhausts (`额度/余额/insufficient quota`) or rejects (401 / `无效的令牌`) is marked disabled and the active pointer moves to the next usable key, so the harness retry of the failed step resolves a different key.
- Route retry policy retries `QUOTA`, `AUTH`, and `INVALID_REQUEST` in addition to the defaults: the first two make rotation reachable, the last absorbs this gateway's misleading 400 when an upstream channel is dead.
- A Responses request without a `prompt_cache_key` is refused by the gateway's Codex-group check with 403. The harness supplies a session id; the plugin adds a per-process fallback when a caller does not.
- Balance display: the settings section lists every key with its available/used quota, reset period, and state; the composer shows the active key's remaining balance. Reads come from `/api/usage/token/` with a host fallback, plus the account's `/v1/dashboard/billing/*` pair.
- Validation: 39 offline tests (key ring, balance parsing and fallback, failure classification, catalog contract, stream guard, `apply()` wiring with and without a connection service, and the real `PiAiAdapter` resolving every advertised model and preparing its call). `scripts/live-check.mjs` verified against the live gateway: balance read, one answer from each of the three models, a rotation rehearsal with an invalid key in front of the real one, and the host adapter classifying the rejected key as `AUTH`.
- The plugin injects only `llm` and `credentials`; the browser RPC surface is requested through `ctx.inject(['connection', 'webServer'], …)`. An isolated end-to-end boot (headless profile in a scratch `DSH_HOME`) proved this matters: with `connection` in the inject list the entry stayed pending and the boot failed, and without it the same boot answered through `packycode/gpt-6.1-sol`.
- Default key names no longer collide after a removal: the ring shrinks when a key is deleted, so `Key N` numbering follows the highest name in use instead of the key count (removing the first of two keys and adding another used to produce a second "Key 2").
- The balance card lists one row per key/account (PackyCode token name, remaining, used, limit, reset period, active/disabled state), and the key rows show only the label plus that same account name so the two line up; the site-wide account total moved to a summary line. The account read now walks past a key the gateway rejects instead of letting whichever key sits first blank the total.
- The package also ships an entry patch for the `connection` row: `inject: [credentials, webRuntime, webServer]`. Connection registers a channel through `owner.webServer` read on *its own row's fiber*, so the shipped `dsh-web-app` row (which injects `webRuntime` alone) made every browser call answer HTTP 405 while the boot log stayed clean. Verified in a scratch web profile over the real HTTP transport: `POST /packycode-api/status` moved from 405 to 401 (registered, unauthorized), and with the root token exchanged for its cookie `status`, `keys/add`, and `balance` all returned their projections — including a live per-key balance and account total, with no key material in any response.
- `claude-sonnet-5-5` and `claude-haiku-5-5` join the catalog, CLI-backed like `claude-opus-5-5`. A session-title request (`purpose: 'session-title'`) on any CLI-backed model now runs on `claude-haiku-5-5`, read-only, in a temp directory (so no project memory is loaded), with the title instructions passed as `--append-system-prompt` and only the request text as the prompt — instead of a full Opus delegated turn in the workspace for every new session.
- The settings section now has a **Claude Code CLI** card: it detects whether this device has the CLI and shows its version (`claude --version`, run in the plugin's isolated config home) and location; without one it warns that the Claude Opus model cannot work and offers an **Install** button that runs `npm install -g @anthropic-ai/claude-code` on the host — the same command on macOS and Windows. The install starts over `claude-cli/install` and the panel polls `claude-cli/status`, so no request is held open for minutes; failures are classified (`npm-missing`, `permission`, `network`, `timeout`, `not-found-after-install`) with npm's last output lines. Lookup covers the official installer, npm/Homebrew/Volta/nvm locations, `%APPDATA%\npm` on Windows, PATH with each platform's rules (Windows `Path`, quoted entries), and finally `npm prefix -g`, because a GUI-launched host's PATH is usually shorter than a terminal's. The runner resolves the CLI per run, so a CLI installed after startup is used without a restart, and puts the CLI's directory on the child's PATH so an npm launcher's `env node` resolves. On Windows an npm `claude.cmd` launcher is never run through `cmd.exe` (Node requires a shell for `.cmd`, which would make `cmd.exe` parse the prompt): the runner reads the launcher and starts the program it forwards to (`node …\cli.js` or a packaged `.exe`) directly. A turn whose CLI is missing now says so and points to the install button instead of `spawn claude ENOENT`.
- The Claude Code CLI's mode now follows the session's own permission preset by default (`claudeCliMode: auto`), so installing the plugin needs no profile patch: `read-only` → `read-only`, `workspace-write` → `edit`, `danger-full-access` with approval `never` → `full`. The CLI cannot ask the harness user for approval, so a session that still asks never gets `full`. The `claude_code` tool's `mode` argument is capped at the same ceiling, and an explicit `read-only`/`edit`/`full` setting still pins the mode. Read through `ctx.get('sandboxPolicy')` and `ctx.get('approval')`; without either service the previous `edit` default stands.
- A CLI-backed `claude-opus-5-5` turn now shows its work live: the CLI's thinking and every tool call it makes (`▸ Bash · git status`, `▸ Read · …`, plus `✗ …` when a tool fails) stream into a reasoning block while it runs, and its answer streams as text, each run bracketed by `block-start`/`block-end` as the harness stream grammar requires. Before, only answer text was forwarded, so a turn spent in the CLI's own tool loop showed nothing until the end.
- A CLI-backed turn's usage now carries cache traffic. The CLI's requests are almost entirely cache hits (`input_tokens: 2`, `cache_read_input_tokens: 42880`), and only `input_tokens` was forwarded, so the session showed a 0% cache hit rate and a context of a few tokens. The prompt side now comes from the CLI's **last** request (uncached input, cache read, cache write) — the harness reads it as context occupancy, which a sum over a multi-step CLI turn would overstate — and output is the CLI's whole-turn total.
- The CLI's stdout and stderr are decoded as UTF-8 on the stream instead of chunk by chunk, so a multi-byte character (Chinese text, emoji) that straddles two pipe reads no longer turns into `�` in the answer, the live reasoning, or a failure message; the same applies to `npm` and `claude --version` output. A consumer that stops reading a streaming CLI turn early now stops the CLI instead of leaving it running until its 30-minute timeout.
- `claude-opus-5-5` is now served by the **local official Claude Code CLI**: selecting that model runs the CLI per turn instead of an HTTP request, which is the only client PackyCode's `cc` group serves Claude models to. The route dispatches per model, so `deepseek-flash` and `gpt-6.1-sol` keep the pi-ai path. A delegated turn drops the harness system prompt and tool schemas (the CLI brings its own), renders the recent conversation into the CLI prompt, and streams the CLI's text back as harness chunks. New settings: `claudeCliPath`, `claudeCliMode` (`read-only`/`edit`/`full`, default `edit`), `claudeCliCwd` (empty = the session's workspace, resolved through the `agents` service). Verified live through the plugin's own adapter: `claude-opus-5-5` → `finish=stop`, `adapter-cli-ok`, 3s, while the HTTP-backed models kept answering.
- New `claude_code` tool: a delegated task is run by the **local official Claude Code CLI**, which is the only client PackyCode's `cc` group serves its Claude models to. The child process receives this plugin's endpoint and API key plus an isolated `CLAUDE_CONFIG_DIR` — required because `~/.claude/settings.json` env overrides an inherited environment, so without it the user's own CLI configuration would silently win. `mode` bounds the CLI's own tools (`read-only` / `edit` / `full`). Verified live through the plugin's runner against the real CLI and gateway: `cli-bridge-ok`, 4s, $0.1984; and offline by a stub-CLI test that asserts the argv, environment isolation, session-workspace cwd, and rendered result. Unlike a forged client identity this runs the genuine binary, so the group's requirement is met rather than bypassed; the trade-offs (per-call cost, tens-of-seconds latency, and the CLI's own tools running outside the harness's sandbox and transcript) are documented in the README.
- A gateway group that serves only the vendor's official client (for example PackyCode's `cc` group answering `403 This API endpoint is only accessible via the official Claude CLI`) is now recognised as a client-policy refusal: the plugin does not retry it, does not disable or rotate a key, and replaces the bare 403 — which the harness renders as an invalid-API-key problem — with a sentence naming the real cause and the groups that do serve API clients. Verified live: the harness receives `PI_AI_ERROR` (outside the route's retryable codes) with no key rotated, while `deepseek-flash` and `gpt-6.1-sol` keep answering.
- The balance card's headline figures are now the **sum of the listed keys** (remaining, used, limit) instead of PackyCode's account-level billing numbers, which count every token on the account and read as a wrong total when several keys are stored. Keys whose read failed are excluded and reported in a note; a key with no quota limit marks the total as unlimited rather than inflating a limit. The account-level numbers remain, on their own clearly-labelled line. Verified in a real browser against the app's own 0.2.0 runtime with two keys: `合计剩余 US$999.07 · 合计已用 US$0.93 · 合计额度 US$1,000.00`, with the account line reading `PackyCode 账号（含同账号其它用量）：剩余 US$407.00 · 已用 US$93.00 · 额度 US$500.00`.
- The route retries up to 20 times (was 3) for every model it serves. One route carries all three models, so the budget is shared: this gateway drops an upstream channel or key per request, and the retry is also what reaches the next key. With the default backoff (500 ms doubling, capped at 10 s, 10% jitter) a failure is surfaced after roughly three minutes of retrying instead of about seven seconds.
- The browser half sets a default `payload` on every channel call. Connection's request envelope requires the field, and `JSON.stringify` drops an `undefined` one, so `call('status')` was refused with `invalid client-request message` and the settings panel showed a read failure. Reproduced in a real browser against the app's own 0.2.0 runtime (`payload` omitted → rejected, `payload: {}` → accepted) and verified fixed there: opening Settings → PackyCode, pasting a key, and clicking Add now renders the account row (`战魂銘人-张洋凡 · 使用中 · 剩余 US$499.07 · 已用 US$0.93 · 额度 US$500.00 · 每月`), the account totals, and the key row with its matching account name.
